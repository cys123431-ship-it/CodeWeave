# 첫 C 프로그램의 구조

## 단원 개요

이 단원은 `Hello, CodeWeave!`를 출력하는 짧은 프로그램을 소스에서 실행 결과까지 추적한다. 코드를 외우는 데서 멈추지 않고 전처리, 번역, 목적 파일, 링크, 실행, 표준 출력, 종료 상태가 서로 다른 책임이라는 사실을 배운다.

여기서 설명하는 `.c` → `.o` → 실행 파일 흐름은 GCC 같은 흔한 도구 체인을 이해하기 위한 모델이다. C 표준은 추상적인 번역 과정과 프로그램의 동작을 규정하지만 특정 명령 이름, 목적 파일 확장자, 실행 파일 형식을 고정하지 않는다.

## 필요한 이유

초보자는 흔히 “실행이 안 된다”는 한 문장으로 모든 문제를 묶는다. 실제로는 다음 실패가 서로 다르다.

- 전처리 단계에서 헤더를 찾지 못한다.
- 번역 단계에서 문법이나 자료형이 맞지 않는다.
- 링크 단계에서 선언한 함수의 정의를 찾지 못한다.
- 프로그램은 실행되지만 출력이 예상과 다르다.
- 출력은 맞지만 종료 상태가 실패를 나타낸다.

단계를 구분하면 진단 메시지가 무엇을 고치라고 말하는지 훨씬 정확하게 읽을 수 있다. 이후 다중 파일, 라이브러리, 테스트 자동화에서도 같은 구분을 계속 사용한다.

## 선수 지식

- 텍스트 파일을 저장할 수 있다.
- 터미널에서 한 줄의 명령을 실행할 수 있다.
- 괄호 `()`, 중괄호 `{}`, 큰따옴표 `""`, 세미콜론 `;`을 눈으로 구분할 수 있다.

변수, 포인터, 메모리 주소는 아직 몰라도 된다.

## 학습 목표

학습 후에는 다음을 할 수 있어야 한다.

1. 전처리, 번역, 링크, 실행을 서로 다른 단계로 설명한다.
2. `#include <stdio.h>`와 `printf` 선언의 관계를 말한다.
3. `int main(void)`가 호스트 C 프로그램의 이식 가능한 시작 형태임을 안다.
4. 문자열 리터럴과 `\n`의 역할을 설명한다.
5. `printf`의 반환값과 프로그램 종료 상태를 구분한다.
6. 경고 없는 컴파일, 정확한 출력, 성공 종료를 각각 검사한다.

## 핵심 이론

### 1. 소스 파일과 번역 단위

사람이 작성하는 `hello.c`는 C 소스 파일이다. 전처리 지시문이 처리된 뒤 컴파일러가 보게 되는 입력을 번역 단위라고 부른다. 파일 하나와 번역 단위 하나를 항상 완전히 같은 것으로 생각하면 매크로와 포함 파일을 배울 때 혼란이 생긴다.

```c
#include <stdio.h>
```

`#include`는 함수 호출이 아니라 전처리 지시문이다. `<stdio.h>`가 제공하는 선언 덕분에 컴파일러는 `printf`의 이름, 매개변수 규칙, 반환형을 알고 호출을 검사할 수 있다. “헤더 내용을 붙인다”는 말은 유용한 설명 모델이지만 구현이 파일의 문자를 물리적으로 복사해야 한다는 언어 보장은 아니다.

### 2. 전처리 → 번역 → 목적 파일

흔한 도구 체인에서는 다음 순서로 생각할 수 있다.

1. 전처리기가 포함 지시문과 매크로를 처리한다.
2. 컴파일러가 문법과 자료형을 검사하며 번역한다.
3. 어셈블 과정을 거쳐 목적 파일을 만든다.

GCC에서는 학습용으로 다음 명령을 사용할 수 있다.

```sh
gcc -std=c11 -Wall -Wextra -Werror -Wpedantic -c hello.c -o hello.o
```

`hello.o`라는 이름과 `gcc` 옵션은 이 도구의 인터페이스다. Windows의 다른 도구는 `.obj` 같은 이름을 쓸 수 있으며, 구현이 중간 파일을 사용자에게 보여 주지 않을 수도 있다.

### 3. 링크는 선언과 정의를 연결한다

목적 파일만으로 프로그램이 완성되지 않을 수 있다. 링커는 여러 목적 파일과 필요한 라이브러리 정의를 연결해 실행 가능한 결과를 만든다.

```sh
gcc hello.o -o hello
```

헤더의 선언 덕분에 `printf` 호출 자체는 번역되었더라도, 필요한 정의를 링크하지 못하면 실행 파일을 만들 수 없다. 문법 오류와 링크의 `undefined reference`를 같은 문제로 보지 않는 이유다.

한 번에 다음처럼 실행하면 GCC 드라이버가 필요한 단계를 순서대로 호출한다.

```sh
gcc -std=c11 -Wall -Wextra -Werror -Wpedantic hello.c -o hello
```

### 4. `main`은 호스트 환경의 시작 함수다

```c
int main(void)
```

`int`는 `main`이 종료 상태를 반환한다는 뜻이다. `void`는 이 형태가 인자를 받지 않는다는 뜻이다. 명령줄 인자를 받는 또 다른 표준 형태도 있지만 이 단원에서는 사용하지 않는다.

`void main`은 이식 가능한 표준 시작 형태가 아니다. 특정 구현에서 허용되는 모습을 모든 C 환경의 보장처럼 사용하지 않는다. 또한 운영체제 없이 동작하는 프리스탠딩 환경은 시작 방식이 다를 수 있으므로, 이 단원은 일반 PC의 호스트 환경을 대상으로 한다.

C99 이후에는 `main`의 닫는 중괄호까지 도달하는 것이 `return 0;`과 같은 성공 종료로 처리된다. 그래도 첫 단원에서는 다음 계약을 명시적으로 보이기 위해 `return 0;`을 적는다.

```c
return 0;
```

0은 호스트 환경에 성공을 알린다. 0이 아닌 값은 실패를 나타내는 데 사용할 수 있지만 구체적인 숫자의 의미를 모든 운영체제가 똑같이 해석한다고 가정하면 안 된다.

### 5. 함수 몸체와 명령문

중괄호는 `main`의 몸체를 묶는다. 함수 호출과 `return` 문은 세미콜론으로 끝난다.

```c
{
    printf("Hello, CodeWeave!\n");
    return 0;
}
```

세미콜론을 빠뜨리면 컴파일러가 다음 줄에서야 문장이 끝나지 않았음을 알아차릴 수 있다. 진단이 가리키는 줄과 그 바로 앞 줄을 함께 살피는 습관이 필요하다.

### 6. 문자열 리터럴과 널 문자

다음 큰따옴표 안의 내용은 문자열 리터럴이다.

```c
"Hello, CodeWeave!\n"
```

문자열 리터럴은 끝에 널 문자를 포함하는 `char` 배열 형태의 객체다. 정적 저장 기간을 가지지만, 문자열 리터럴의 원소를 수정하려는 동작은 정의되지 않은 동작이다. 따라서 출력할 읽기 전용 데이터처럼 다룬다.

`\n`은 역슬래시와 `n` 두 문자를 그대로 출력하라는 뜻이 아니라 새 줄 문자를 나타내는 이스케이프 시퀀스다. 텍스트 스트림에서 그 문자가 실제 장치의 줄 끝 바이트로 어떻게 변환되는지는 구현 환경에 따라 달라질 수 있다. 학습 문제는 논리적인 출력 텍스트와 마지막 개행을 계약으로 삼는다.

### 7. `printf`의 반환값

`printf`는 성공하면 기록한 문자 수에 해당하는 음수가 아닌 값을 반환한다. `printf`의 반환값이 음수이면 출력 오류 또는 인코딩 오류가 보고된 것이다.

```c
if (printf("Hello, CodeWeave!\n") < 0) {
    return 1;
}
```

이 검사는 호출 중 즉시 보고된 실패를 종료 상태에 반영한다. 표준 출력이 버퍼링되면 나중의 flush나 스트림 닫기에서 오류가 보고될 가능성까지 이 한 줄이 모두 검출하는 것은 아니다. 첫 실습의 범위를 넘어서는 완전한 I/O 오류 처리는 뒤의 표준 입출력 단원에서 다룬다.

### 8. 세 가지 성공 조건

첫 프로그램도 최소 세 관점으로 검사한다.

| 관점 | 성공 조건 | 대표 실패 |
| --- | --- | --- |
| 번역·링크 | 경고와 오류 없이 실행 파일 생성 | 세미콜론 누락, 정의 누락 |
| 표준 출력 | `Hello, CodeWeave!` 뒤에 개행 | 철자·공백·개행 오류 |
| 종료 상태 | 0 | `return 1;` |

컴파일 성공만으로 출력이 맞음을 증명하지 못하고, 화면에 글자가 보였다는 사실만으로 종료 상태 0을 증명하지 못한다.

## 정적 도식 읽기

화면의 독자 제작 SVG는 위쪽에서 `hello.c` → 전처리 → 번역으로 이동하고, 목적 파일 → 링크 → 실행 프로그램으로 이어진다. 프로그램을 실행하면 표준 출력은 별도로 관찰하고, 호스트에는 종료 상태 0을 돌려준다.

이 도식은 런타임 애니메이션이 아니다. 각 단계의 책임을 고정한 학습 지도이며, 중간 파일 이름과 실제 하위 도구 구성은 구현에 따라 달라질 수 있다.

## 단계별 예제

먼저 헤더와 빈 `main`을 만든다.

```c
#include <stdio.h>

int main(void) {
    return 0;
}
```

이 프로그램은 성공 종료하지만 인사 문구를 출력하지 않는다. 다음으로 출력 호출을 추가한다.

```c
printf("Hello, CodeWeave!\n");
```

마지막으로 `printf`가 즉시 보고한 실패를 종료 상태에 반영한다.

```c
if (printf("Hello, CodeWeave!\n") < 0) {
    return 1;
}
```

위의 짧은 코드 두 개는 함수 몸체 안에 들어갈 **조각**이다. 아래 코드는 헤더와 `main`을 모두 가진 **완성 프로그램**이다.

## 완성 프로그램

```c
#include <stdio.h>

int main(void) {
    if (printf("Hello, CodeWeave!\n") < 0) {
        return 1;
    }
    return 0;
}
```

## 실행 결과

```text
Hello, CodeWeave!
```

위 표시에서는 마지막 개행 때문에 커서가 다음 줄로 이동한다. `\n`이라는 두 글자가 화면에 보이는 것은 아니다.

## 왜 이런 결과가 나오는가

1. `stdio.h`를 통해 `printf` 선언을 사용할 준비를 한다.
2. 호스트 환경이 `main`을 호출한다.
3. `printf`가 문자열의 널 문자 전까지 기록한다.
4. `\n`이 새 줄 문자로 처리된다.
5. 즉시 출력 오류가 없으면 `printf` 결과는 음수가 아니다.
6. `return 0;`이 성공 종료를 호스트에 알린다.

## 흔한 오류

### 세미콜론 누락

```c
printf("Hello, CodeWeave!\n")
return 0;
```

첫 줄 끝의 세미콜론이 없으므로 번역 오류다. 진단은 `return`이 있는 다음 줄을 가리킬 수도 있다.

### 스마트 따옴표 사용

문서 편집기가 `"`를 `“`와 `”`로 바꾸면 C 문자열 구분자가 아니다. 소스 코드에는 ASCII 큰따옴표를 사용한다.

### `\n`을 문자열 밖에 쓰기

이스케이프 시퀀스는 문자나 문자열 리터럴 안에서 사용한다. 큰따옴표 밖의 `\n`은 원하는 개행 출력 코드가 아니다.

### `void main`으로 변경

어떤 도구가 받아들였다는 사실만으로 이식 가능한 호스트 C 프로그램이 되지는 않는다. 이 단원에서는 `int main(void)`를 사용한다.

### 출력만 보고 종료 상태를 놓치기

문구를 출력한 뒤 `return 1;`을 실행하면 화면은 맞아 보여도 자동 테스트는 실패 종료로 판정할 수 있다.

## 중간 점검

1. `#include <stdio.h>`는 실행 중 호출되는 함수인가?
2. 목적 파일과 실행 프로그램은 어떤 단계로 구분되는가?
3. `int main(void)`에서 첫 번째 `void`가 아니라 괄호 안의 `void`는 무엇을 뜻하는가?
4. `printf`의 성공 반환값과 `main`의 성공 반환값은 같은 의미인가?
5. `\n`은 소스에서 두 문자로 보이는데 출력에서는 왜 줄을 바꾸는가?

정답을 코드 줄 번호가 아니라 “전처리”, “링크”, “함수 반환값”, “종료 상태” 같은 개념어로 설명해 보자.

## 개념 확인 퀴즈

`printf("C\n");`의 논리적인 출력은 무엇인가?

- 정답: `C`를 기록한 뒤 다음 줄로 이동한다.
- 오답 점검: 역슬래시와 `n`이 그대로 보인다고 생각했다면 이스케이프 시퀀스와 문자열의 소스 표기를 다시 구분한다.

## 핵심 요약

- 헤더 선언을 준비하는 전처리와 소스를 번역하는 단계는 역할이 다르다.
- 목적 파일은 링크를 거쳐 실행 프로그램의 일부가 된다.
- `int main(void)`는 인자를 받지 않는 이식 가능한 호스트 프로그램 시작 형태다.
- 문자열 리터럴은 수정하지 않는다. 수정 시도는 정의되지 않은 동작이다.
- `\n`은 새 줄 문자이고, `printf`의 음수 반환은 출력 오류를 뜻한다.
- 정확한 출력과 종료 상태 0을 별도로 검사한다.

## 기초 코딩 연습

`Hello, CodeWeave!`와 마지막 개행을 정확히 출력하라. 먼저 예상 출력의 공백, 대소문자, 문장 부호를 적고 코드를 작성한다.

## 응용 연습

두 번의 출력 호출로 다음 두 줄을 만든다.

```text
source -> build
run -> check
```

각 `printf`의 반환값을 따로 검사하고 어느 호출이 실패했는지 서로 다른 0이 아닌 종료 상태로 구분해 보자. 그 숫자의 의미는 이 프로그램 내부의 정책임을 주석으로 명시한다.

## 도전 문제

`puts`와 `printf`로 같은 한 줄을 출력하는 두 프로그램을 만들고 반환값 계약을 비교하라. 단순히 둘 다 “출력 함수”라고 결론내리지 말고, `puts`가 문자열 뒤에 새 줄을 추가하는 점과 성공 반환값의 정확한 숫자를 이식 가능한 계약으로 가정하면 안 되는 점을 적는다.

**첫 빌드 관찰표**를 작성한다.

1. 정상 소스의 컴파일 명령, 출력, 종료 상태를 기록한다.
2. 세미콜론을 하나 지우고 번역 진단을 기록한다.
3. 별도 파일에 선언만 두고 정의를 빼 링크 진단을 기록한다.
4. `return 1;`로 바꿔 출력과 종료 상태가 독립적임을 확인한다.
5. 원래 코드로 되돌리고 모든 검사를 다시 통과시킨다.

진단 전문을 교육 사이트에 답처럼 하드코딩하지 말고, 사용한 컴파일러와 환경에 따라 표현이 달라질 수 있음을 함께 기록한다.

## 테스트와 풀이 개선

GCC가 있는 환경에서는 다음처럼 경고를 켠다.

```sh
gcc -std=c11 -Wall -Wextra -Werror -Wpedantic hello.c -o hello
./hello
```

채점기와 같은 옵션이며, `-Werror` 때문에 경고도 컴파일 실패로 처리한다. 진단을 확인해 경고를 고친 뒤 다시 제출한다.

자동 검사는 다음을 별도로 확인해야 한다.

- 컴파일과 링크가 성공했는가?
- 표준 출력이 `Hello, CodeWeave!\n`과 정확히 같은가?
- 표준 오류에 예상하지 않은 진단이 있는가?
- 프로세스 종료 상태가 0인가?

오답을 수정한 뒤에는 “코드가 달라졌다”만 적지 말고 전처리, 번역, 링크, 출력, 종료 중 어느 계약을 고쳤는지 제출 기록에 남긴다.

## 복습 연결

다음 변수·자료형 단원에서는 `main` 안에 이름이 붙은 값을 만든다. 넘어가기 전에 다음을 코드에서 직접 가리킬 수 있어야 한다.

- `printf` 선언을 준비하는 줄
- 프로그램 시작 함수의 머리와 몸체
- 문자열 리터럴과 개행 이스케이프
- 출력 오류를 판단하는 비교
- 성공 종료 상태를 반환하는 줄

하나라도 설명하기 어렵다면 완성 프로그램을 보지 않고 다시 입력하고, 컴파일 → 실행 → 출력 → 종료 상태 순서로 확인한다.
