# `fgets`로 첫 논리적 한 줄 읽기

> 이 원고와 예제·문제는 CodeWeave용으로 새로 작성했습니다. 상용 교재의 본문·그림·문제를 복제하지 않았습니다.

## 단원 개요

`fgets`는 흔히 “한 줄을 읽는 함수”라고 소개되지만, 버퍼가 작으면 한 줄의 일부만 읽고도 정상적으로 반환합니다. 이 단원에서는 `char chunk[8]`처럼 의도적으로 작은 버퍼를 반복 사용해 첫 논리적 한 줄의 바이트 길이를 구합니다. 한 번의 호출 결과와 입력의 한 줄을 구분하는 것이 핵심입니다.

## 선수 지식

- 문자 배열과 널 종료 문자 `\0`
- 배열의 읽기 가능한 범위와 `sizeof`
- `size_t`, 반복문, `stdin`
- 함수 반환값으로 성공과 실패를 구분하는 방법

## 학습 목표

학습을 마치면 다음을 할 수 있어야 합니다.

1. `fgets(buffer, size, stream)`가 한 번에 저장하는 최대 입력 바이트 수를 설명한다.
2. 개행이 저장된 조각과 버퍼가 먼저 가득 찬 조각을 구분한다.
3. 여러 조각을 첫 개행까지 소비해 한 논리적 줄을 완성한다.
4. 빈 줄, 개행 없는 마지막 줄, 입력 없는 EOF, 입력 오류를 서로 다르게 처리한다.
5. C의 `char` 순회가 사용자에게 보이는 글자 수가 아니라 바이트 수를 센다는 한계를 설명한다.

## 핵심 이론

### 1. `fgets`의 크기 인수는 버퍼 전체 용량이다

```c
char chunk[8];
fgets(chunk, sizeof chunk, stdin);
```

성공한 호출은 최대 `sizeof chunk - 1`, 즉 7바이트의 입력을 저장합니다. 남은 한 칸에는 널 종료 문자 `\0`을 씁니다. 7바이트를 저장하기 전에 개행을 만나면 개행 문자 `\n`도 버퍼에 저장한 뒤 널 종료합니다.

따라서 성공한 결과는 C 문자열이지만, 그 문자열이 입력 줄 전체라고 보장되지는 않습니다.

### 2. 버퍼 조각과 논리적 한 줄은 서로 다른 경계다

이 단원에서 논리적 한 줄은 개행 직전까지의 입력입니다. 입력이 다음과 같다고 합시다.

```text
ABCDEFGHIJK\n
```

8칸 버퍼로 읽으면 개념적으로 다음과 같이 나뉩니다.

| 호출 | 저장된 입력 | 널 종료 | 의미 |
|---|---|---|---|
| 첫 번째 | `ABCDEFG` | `\0` | 줄은 아직 끝나지 않았을 수 있음 |
| 두 번째 | `HIJK\n` | `\0` | 개행을 발견했으므로 첫 줄 완료 |

널 종료 문자는 각 버퍼 조각의 저장 경계입니다. 개행 문자는 입력의 줄 경계입니다. 둘을 같은 것으로 취급하면 긴 줄을 첫 조각 길이인 7로 잘못 계산합니다.

### 3. 정확한 경계가 중요한 이유

입력 내용이 정확히 7바이트이고 그 다음이 개행이면, 첫 호출에는 내용 7바이트와 `\0`만 들어갑니다. 개행은 스트림에 남아 두 번째 호출에서 읽힙니다.

개행이 없다는 사실만으로 줄이 잘렸다고 단정하면 안 됩니다. 현재 조각에 개행이 없다는 사실은 “다음 입력을 확인해야 한다”는 뜻일 뿐입니다. 다음 호출이 개행을 읽을 수도 있고, 더 많은 내용을 읽을 수도 있고, 개행 없는 정상 EOF를 만날 수도 있습니다.

### 4. `fgets`가 `NULL`을 반환한 뒤 상태를 해석한다

`fgets`의 반환값이 `NULL`이면 새 조각을 얻지 못했습니다. 그 뒤에는 다음 상태를 구분합니다.

EOF 전에 읽은 바이트가 하나도 없으면 `NO INPUT`을 출력한다는 것이 이 실습의 명시적 계약입니다.

- `ferror(stdin)`이 참: 입력 오류입니다. 정상 길이를 발표하지 않습니다.
- 오류가 아니고 이전에 읽은 바이트가 없음: 입력 없는 깨끗한 EOF이므로 `NO INPUT`을 출력합니다.
- 오류가 아니고 이전에 읽은 데이터가 있음: 개행 없는 마지막 줄이 EOF로 끝난 것이므로 누적 길이를 출력합니다.

`feof`와 `ferror`는 읽기 시도의 결과를 설명합니다. 읽기 전에 `while (!feof(stdin))`처럼 검사하여 반복을 제어하는 방식은 마지막 실패 호출을 자연스럽게 처리하지 못하므로 피합니다.

### 5. 빈 줄과 입력 없음은 다르다

빈 줄에는 실제로 개행이 있습니다. 첫 `fgets`가 `"\n"`을 성공적으로 돌려주고, 개행 앞의 바이트 수는 0입니다. 반면 크기가 0인 입력 스트림에서는 첫 호출부터 EOF를 만나 아무 조각도 얻지 못합니다.

이 단원의 출력 계약은 다음과 같습니다.

| 입력 상태 | 출력 |
|---|---|
| 빈 줄 `\n` | `0` |
| `CAT\n` | `3` |
| `CAT` 뒤 즉시 EOF | `3` |
| 즉시 EOF | `NO INPUT` |
| 읽기 오류 | 성공 결과를 출력하지 않고 비정상 상태 반환 |

### 6. 길이는 바이트 단위다

배열을 `char` 단위로 순회하여 더한 값은 바이트 수입니다. UTF-8로 인코딩된 한국어 한 글자는 여러 바이트일 수 있으므로 화면에 보이는 글자 수와 같지 않을 수 있습니다. 이 문제는 바이트 길이를 요구합니다. 유니코드 문자 수를 세는 문제라면 인코딩 검증과 코드 포인트 해석이 별도로 필요합니다.

## 단계별 예제

### 1단계: 한 조각에서 개행 위치 찾기

아래 조각은 단독 완성 프로그램이 아니라 이후 반복문 안에 들어갈 코드입니다.

```c
size_t i = 0;
while (chunk[i] != '\0' && chunk[i] != '\n') {
    ++i;
}
total += i;
```

성공한 `fgets` 결과는 널 종료되므로 현재 조각 안에서 이 반복은 멈춥니다. `chunk[i] == '\n'`이면 첫 논리 줄이 끝났습니다. `chunk[i] == '\0'`이면 다음 조각을 시도해야 합니다.

### 2단계: 읽은 적이 있는지 기록하기

`saw_input`은 빈 줄과 즉시 EOF를 구분합니다. `fgets`가 성공하면 입력 바이트 수가 0인 조각이라도 호출 자체는 성공했으므로 1로 바꿉니다.

```c
int saw_input = 0;

if (fgets(chunk, sizeof chunk, stdin) != NULL) {
    saw_input = 1;
}
```

### 3단계: 완성 프로그램

다음 코드는 그대로 컴파일할 수 있는 완성 프로그램입니다.

```c
#include <stddef.h>
#include <stdio.h>

int main(void) {
    char chunk[8];
    size_t total = 0;
    int saw_input = 0;

    for (;;) {
        if (fgets(chunk, sizeof chunk, stdin) == NULL) {
            if (ferror(stdin)) {
                return 1;
            }
            if (!saw_input) {
                puts("NO INPUT");
                return 0;
            }
            break;
        }

        saw_input = 1;
        size_t i = 0;
        while (chunk[i] != '\0' && chunk[i] != '\n') {
            ++i;
        }
        total += i;

        if (chunk[i] == '\n') {
            break;
        }
    }

    printf("%zu\n", total);
    return 0;
}
```

일반 제품에서 입력 크기를 제한하지 않는다면 `total += i` 전에 `SIZE_MAX - total < i`인지 확인하는 넘침 정책도 필요합니다. 이 교육 문제의 채점 입력은 그 범위를 넘지 않습니다.

## 실행 결과

```text
입력: 1234567\n
출력: 7
```

첫 호출 뒤에는 개행이 없지만 두 번째 호출이 개행을 읽고 종료합니다.

```text
입력: abcdefghijklmnopqrstuvwxyz\n
출력: 26
```

여러 조각을 소비하더라도 첫 줄의 모든 바이트를 합칩니다.

```text
입력: first\nsecond\n
출력: 5
```

첫 개행 뒤의 두 번째 줄은 이 문제의 처리 대상이 아닙니다.

## 흔한 오류

1. **`strlen`을 한 번만 호출한다**: 첫 조각의 길이만 얻어 긴 줄을 누락합니다.
2. **개행을 길이에 포함한다**: `\n`을 확인하기 전에 더하면 논리적 내용보다 1 크게 계산합니다.
3. **정확히 7바이트면 끝났다고 가정한다**: 남은 개행을 소비하지 않아 다음 입력 처리까지 꼬일 수 있습니다.
4. **EOF에서 누적 데이터를 버린다**: 개행 없는 마지막 줄도 유효한 줄일 수 있습니다.
5. **빈 줄과 즉시 EOF를 같은 0으로 출력한다**: 입력 계약의 서로 다른 상태를 감춥니다.
6. **`while (!feof(stdin))`를 사용한다**: EOF 표시는 실패한 읽기 뒤 설정되므로 반환값 중심 구조가 더 정확합니다.
7. **글자 수라고 부른다**: 이 알고리즘이 세는 것은 인코딩된 바이트 수입니다.

## 중간 점검

1. `char chunk[8]`이 입력 내용 8바이트를 한 번에 저장할 수 없는 이유는 무엇인가요?
2. 첫 조각에 개행이 없을 때 확실히 알 수 있는 사실은 무엇인가요?
3. 빈 줄에서 `fgets`는 성공할까요?
4. 개행 없는 데이터 뒤 EOF와 즉시 EOF를 어떤 상태로 구분하나요?
5. `ferror(stdin)`이 참일 때 누적 길이를 정상 결과로 출력하면 왜 문제가 될까요?

## 핵심 요약

- 한 번의 `fgets` 결과는 한 논리적 줄의 일부일 수 있습니다.
- 성공 시 최대 `size - 1`바이트를 저장하고 널 종료합니다.
- 개행은 공간이 있으면 저장되며 논리 줄의 끝을 알려 줍니다.
- 정확한 버퍼 경계에서는 다음 호출로 개행 또는 EOF를 확인해야 합니다.
- `NULL` 반환 뒤 입력 오류, 즉시 EOF, 데이터 뒤 EOF를 구분합니다.
- 이 문제의 결과는 유니코드 글자 수가 아니라 바이트 수입니다.

## 도전 문제

첫 줄이 지정한 최대 바이트 수를 넘으면 남은 줄을 끝까지 소비하되 결과는 `TOO LONG`으로 표시하세요. 이후 다음 줄을 처리할 수 있도록 스트림 위치를 올바르게 정리해야 합니다. 제한을 초과한 뒤에도 `size_t` 누적이 넘치지 않는 설계를 생각합니다.

## 테스트와 풀이 개선

최소한 다음 사례를 차례로 제출해 실패 원인을 분리합니다.

- 짧은 줄 `CAT\n`

## 복습 연결

이 단원은 경계 제한 문자열 순회를 실제 스트림 입력으로 확장합니다. 다음에는 여러 조각을 동적 메모리에 연결하는 방법, 줄을 토큰으로 나누는 방법, 파일 전체를 처리하는 반복 구조를 배울 수 있습니다. Rust에서는 `read_line`과 바이트/UTF-8 문자열 계약을 비교하여 언어와 라이브러리가 경계를 어떻게 표현하는지 살펴볼 수 있습니다.
