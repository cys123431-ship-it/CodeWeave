# 동적 배열: 학생 한 명 안전하게 추가하기

## 단원 개요

이 단원은 앞에서 완성한 `reserve_students`를 조립해 `push_student`를 구현한다. 저장 공간이 남았을 때는 바로 한 칸을 쓰고, 가득 찼을 때만 0→4 또는 두 배의 기하급수 성장 정책을 적용한다. 목표는 단순히 원소를 추가하는 것이 아니라 실패가 발생해도 관찰 가능한 상태를 손상하지 않는 연산을 만드는 것이다.

## 필요한 이유

호출자가 추가할 때마다 `realloc`, 바이트 수 검사, 새 슬롯 초기화를 반복하면 같은 위험한 코드가 여러 곳에 생긴다. 반대로 `push_student`가 “학생 한 명 추가”라는 높은 수준의 계약을 제공하면 호출자는 길이와 용량 계산을 직접 다루지 않아도 된다. 이 분리는 이후 스택, 벡터형 명부, 파일에서 읽은 레코드 누적에도 재사용된다.

## 선수 지식

- `struct Student` 배열과 구조체 전체 대입
- `size_t`, `SIZE_MAX`, 부호 없는 정수의 모듈러 연산
- `length <= capacity` 불변식과 정규 빈 상태
- `reserve_students`의 성장 전용·실패 보존 계약
- 동적 배열의 단일 소유자와 `free`

## 학습 목표

학습 후에는 다음을 할 수 있어야 한다.

1. 여유 슬롯 경로와 용량 확장 경로를 구분한다.
2. 0→4와 이후 두 배 성장 정책을 구현한다.
3. `capacity * 2` 전에 오버플로를 판정한다.
4. 검증된 `reserve_students`를 재사용한다.
5. 확장 성공 뒤에만 레코드와 길이를 공개한다.
6. 기하급수 성장의 상각 비용과 한 번의 확장 비용을 구분한다.

## 핵심 이론

### 1. 세 값이 하나의 상태를 이룬다

동적 배열의 공개 상태는 포인터 하나가 아니다.

- `*students`: 소유한 저장 공간의 시작 주소
- `*length`: 의미 있는 학생 레코드 수
- `*capacity`: 재할당 없이 저장할 수 있는 슬롯 수

항상 `*length <= *capacity`여야 한다. 이 과제의 정규 빈 상태는 `*length == 0`, `*capacity == 0`, `*students == NULL`이다. 양수 용량인데 포인터가 `NULL`이거나 0 용량인데 포인터가 비NULL이면 어느 범위를 읽어도 되는지 계약이 무너지므로 먼저 거부한다.

### 2. 여유 슬롯은 이미 소유한 객체다

`*length < *capacity`이면 `(*students)[*length]`는 할당된 범위 안의 다음 슬롯이다. `struct Student`는 대입으로 두 멤버를 함께 복사할 수 있다.

```c
(*students)[*length] = value;
(*length)++;
```

대입이 끝나기 전 길이를 늘리면 호출자가 아직 쓰지 않은 슬롯을 유효 레코드로 관찰할 수 있다. 따라서 길이는 마지막에 증가시킨다.

### 3. 가득 찼을 때만 성장한다

`*length == *capacity`이면 다음 인덱스는 현재 할당 범위 밖이다. 이때 첫 용량은 4, 이후 용량은 두 배로 정한다.

| 현재 용량 | 다음 용량 |
| ---: | ---: |
| 0 | 4 |
| 4 | 8 |
| 8 | 16 |
| 16 | 32 |

초기 용량 4는 이 과제의 정책이지 C 언어의 규칙이 아니다. 다른 컨테이너는 요구사항에 따라 다른 값을 선택할 수 있지만 한 계약 안에서는 일관되어야 한다.

### 4. 두 배 계산 전에 범위를 확인한다

`size_t`는 부호 없는 정수이므로 범위를 넘는 곱셈은 `SIZE_MAX + 1`을 법으로 하는 값처럼 순환한다. 계산 후 결과가 작아졌는지 추측하지 말고 계산 전에 검사한다.

```c
if (*capacity > SIZE_MAX / 2) return 0;
size_t new_capacity = *capacity * 2;
```

그 뒤 `reserve_students`가 `new_capacity * sizeof(struct Student)`의 바이트 수 오버플로를 별도로 검사한다. 원소 수의 두 배와 바이트 수 곱셈은 서로 다른 두 경계다.

### 5. 낮은 수준의 소유권 변경을 재사용한다

`push_student`가 `realloc`을 직접 호출하면 이전 단원의 임시 포인터, 새 슬롯 초기화, 실패 보존 규칙을 다시 구현해야 한다. 대신 다음 호출로 저장 공간 변경을 위임한다.

```c
if (!reserve_students(students, *length, capacity, new_capacity)) {
    return 0;
}
```

검증된 `reserve_students`는 실패하면 포인터·용량·기존 레코드를 보존한다. `push_student`는 이 계약을 전제로 실패 뒤 새 학생과 길이를 쓰지 않는다.

### 6. 기하급수 성장과 상각 비용

용량을 매번 1만 늘리면 원소를 n개 추가하는 동안 재할당과 복사가 반복되어 전체 이동량이 1 + 2 + … + n에 가까워질 수 있다. 용량을 두 배로 늘리면 한 원소는 새 블록으로 이동되는 횟수가 제한되고, n번 push의 총 이동량을 n의 상수배로 묶을 수 있다. 그래서 여러 연산에 나눈 평균, 즉 상각 비용은 push당 O(1)로 설명한다.

단, 확장이 일어나는 한 번의 push 자체는 기존 원소 수에 비례하는 O(n)일 수 있다. 상각 O(1)을 모든 개별 호출이 항상 O(1)이라는 뜻으로 말하면 안 된다.

## 정적 도식 읽기

화면 도식은 두 갈래를 표시한다.

1. 빈 슬롯이 있으면 현재 `length` 위치에 기록하고 길이를 공개한다.
2. 가득 찼으면 두 배 계산의 오버플로를 검사하고 `reserve_students`를 호출한다.

확장 실패 화살표는 원본 유지로 끝난다. 확장 성공 화살표만 레코드 기록과 길이 증가로 이어진다. 도식은 런타임 애니메이션이 아니라 계약의 순서를 고정한 독자 제작 SVG다.

## 단계별 예제

길이 2, 용량 2인 배열을 생각해 보자.

```text
인덱스       0        1
레코드    101:70   205:88
length = 2, capacity = 2
```

`309:95`를 추가하면 배열이 가득 찼으므로 다음 순서가 필요하다.

1. 2는 `SIZE_MAX / 2`보다 크지 않은지 확인한다.
2. 새 용량 4를 계산한다.
3. `reserve_students(..., 4)`의 성공을 확인한다.
4. 인덱스 2에 `{309, 95}`를 복사한다.
5. 길이를 3으로 증가시킨다.

용량 4의 남은 인덱스 3은 `reserve_students` 계약에 따라 `{0, 0}`으로 초기화되어 있지만 아직 `length` 밖이므로 유효 학생 레코드는 아니다.

## 완성 함수

```c
#include <stddef.h>
#include <stdint.h>

struct Student {
    int id;
    int score;
};

int reserve_students(struct Student **students, size_t length,
                     size_t *capacity, size_t new_capacity);

int push_student(struct Student **students, size_t *length,
                 size_t *capacity, struct Student value) {
    if (students == NULL || length == NULL || capacity == NULL) return 0;
    if (*length > *capacity) return 0;
    if ((*capacity == 0) != (*students == NULL)) return 0;

    if (*length == *capacity) {
        size_t new_capacity;
        if (*capacity == 0) {
            new_capacity = 4;
        } else {
            if (*capacity > SIZE_MAX / 2) return 0;
            new_capacity = *capacity * 2;
        }
        if (!reserve_students(students, *length, capacity, new_capacity)) {
            return 0;
        }
    }

    (*students)[*length] = value;
    (*length)++;
    return 1;
}
```

이 함수는 `reserve_students`의 정의를 포함하지 않는다. 자동 채점 하네스가 같은 원형의 검증된 구현을 다른 번역 단위에서 제공한다. 학습자는 `push_student`의 조립 계약에 집중한다.

## 완성 프로그램

아래 코드는 개념을 연결하는 축약된 호출 예다. 실제로 실행하려면 앞 단원의 `reserve_students` 정의와 종료 시 `free(students)`가 함께 필요하다.

```c
struct Student *students = NULL;
size_t length = 0;
size_t capacity = 0;

if (!push_student(&students, &length, &capacity,
                  (struct Student){309, 95})) {
    /* 실패 처리 */
}
```

이 조각은 단독 완성 프로그램이 아니다. 자동 채점 제출에는 `main`이나 `reserve_students` 정의를 추가하지 않는다.

## 실행 결과

공개 사례의 결과는 다음과 같다.

```text
1 · 길이 3 · 용량 4 · 새 학생 309:95
```

빈 배열에 처음 추가하면 길이는 1, 용량은 4다. 길이 1, 용량 4인 배열에 추가하면 용량을 바꾸지 않고 길이만 2가 된다.

## 왜 이런 결과가 나오는가

공개 사례는 시작할 때 `length == capacity == 2`이므로 성장 경로를 탄다. 두 배 용량 4의 예약이 성공하고 기존 두 레코드가 보존된 다음, 인덱스 2에 새 구조체가 복사된다. 마지막 길이 증가가 인덱스 2를 유효 범위 `[0, 3)` 안에 포함한다.

할당 실패가 주입되면 `reserve_students`가 0을 반환한다. 그 아래의 대입과 `(*length)++`에는 도달하지 않으므로 포인터·길이·용량·기존 두 학생이 모두 그대로 남는다.

## 흔한 오류

- 가득 찬 배열의 `students[length]`에 먼저 써서 범위를 벗어난다.
- `(*length)++`를 확장 성공 확인 전에 수행한다.
- 매번 `capacity + 1`을 사용해 기하급수 성장 계약을 깨뜨린다.
- `*capacity * 2`를 계산한 뒤 오버플로를 검사한다.
- `reserve_students`의 반환값을 무시한다.
- push 안에서 `realloc`을 직접 호출해 검증된 실패 보존 코드를 중복한다.
- 0 용량에서 두 배한 0을 그대로 요청한다.
- `length`, `capacity`, 포인터의 불변식을 검사하기 전에 역참조한다.

호출자가 거짓 capacity와 짧은 실제 블록을 넘기면 C 함수가 포인터만 보고 이를 일반적으로 증명할 수 없다. 이 전제 위반 뒤의 범위 밖 접근은 정의되지 않은 동작이다.

## 개념 확인 퀴즈

가득 찬 배열에 학생을 추가할 때 올바른 순서는 무엇인가?

1. 두 배 계산의 오버플로 확인 → reserve 성공 확인 → 레코드 기록 → 길이 증가
2. 길이 증가 → 레코드 기록 → reserve 호출
3. 레코드 기록 → reserve 호출 → 길이 증가
4. capacity를 먼저 공개하고 실패하면 되돌리기

정답은 1번이다. 성공 전 공개 상태를 바꾸지 않는 순서가 실패 보존 계약을 지킨다.

## 핵심 요약

- `length < capacity`이면 현재 저장 공간에 바로 추가한다.
- 가득 찼을 때만 0→4, 이후 두 배로 성장한다.
- `*capacity > SIZE_MAX / 2`를 곱셈 전에 검사한다.
- 바이트 크기와 `realloc` 소유권 변경은 `reserve_students`에 위임한다.
- 확장 성공 뒤 레코드를 쓰고, 길이는 마지막에 증가시킨다.
- 기하급수 성장은 여러 push의 평균 비용을 낮추지만 개별 확장은 O(n)일 수 있다.

## 테스트와 풀이 개선

자동 채점은 사용자 `push_student`와 서버의 검증된 `reserve_students`를 별도 번역 단위로 링크한다. 정상 여유 슬롯, 마지막 여유 슬롯, 0→4, 1→2, 3→6, 반복 성장, 정수 극값 레코드, NULL 인수 세 종류, 불변식 위반 세 종류, 원소 수 두 배 오버플로, 바이트 크기 오버플로, 주입된 예약 실패를 실제 GCC로 검사한다.

하네스는 reserve 호출 횟수와 요청 용량을 관찰하므로 `capacity + 1`, 불필요한 reserve, 직접 realloc 복제를 구분한다. 유한한 사례는 모든 입력의 메모리 안전이나 상각 복잡도를 수학적으로 증명하지 않는다. 시간 제한과 함수 하네스는 파일·프로세스·네트워크를 막는 공개 실행 격리가 아니다.

실패한 풀이를 고칠 때는 다음 순서로 확인한다.

1. 세 포인터와 상태 불변식을 쓰기 전에 검사했는가?
2. 여유 슬롯에서는 reserve를 건너뛰는가?
3. 0 용량과 양수 용량의 다음 값을 구분했는가?
4. 두 배 계산 전에 `SIZE_MAX / 2`를 확인했는가?
5. reserve 실패 뒤 레코드와 길이를 쓰지 않는가?
6. 성공한 뒤 `value`를 먼저 쓰고 `(*length)++`를 마지막에 하는가?

## 복습 연결

이 단원은 `create_students` → `reserve_students` → `push_student`로 추상화 수준을 한 단계씩 높였다. 다음에는 마지막 원소 제거와 중간 원소 삭제를 구현하면서 객체 수명과 이동 범위를 다룬다. 자료구조 트랙에서는 같은 저장소를 배열 기반 스택에 연결하고, Rust 트랙에서는 `Vec::push`의 소유권·용량 정책과 비교한다.
