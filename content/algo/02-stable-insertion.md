# E02 안정 삽입 정렬: 비교와 이동을 따로 세기

## 1. 개요·필요성·선수 지식·목표
예상 25분. 배열·반복·함수·구조체와 C 구조체 배열 정렬을 먼저 익힌다. 같은 키의 원래 순서를 보존하며 접두부를 정렬하고, 같은 정답 배열이라도 연산 횟수는 입력과 알고리즘에 따라 다름을 관찰한다. 이번 범위는 최대 8개 레코드의 안정 삽입 정렬이다. 다른 정렬법·실제 시간 벤치마크는 후속 범위다.

## 2. 핵심 이론: 정렬된 접두부를 늘린다
첫 원소 하나는 이미 정렬돼 있다. i번째 원소를 지역 변수 key에 보관하고 왼쪽의 더 큰 원소들을 한 칸씩 오른쪽으로 옮긴다. 빈자리에 key 레코드 전체를 놓으면 [0,i+1)이 정렬된다. 원래 key 위치는 이동 중 덮어써도 지역 복사본이 있으므로 값을 잃지 않는다.

## 3. 안정성: 같은 키의 순서는 입력 기준
레코드는 `struct SortItem { int key; int tag; };`다. 정렬 기준은 key 하나이며 tag는 원래 항목을 구별하는 데이터다. 같은 키는 tag 숫자순으로 다시 정렬하지 않는다. `2:20, 1:10, 2:21`의 정답은 `1:10, 2:20, 2:21`이다. 이동 조건을 `>`로 두어 같은 키를 추월하지 않는다. key만 옮기고 tag를 두면 레코드가 훼손된다.

## 4. 횟수 계약: 무엇을 세고 무엇을 빼는가
비교 수는 `items[j-1].key > key.key`를 실제 평가한 횟수다. 거짓이라서 멈춘 마지막 비교도 포함한다. j가 0이면 키 비교는 하지 않는다. 길이 검사·루프 조건은 세지 않는다. 이동 수는 오른쪽 밀기와 마지막 `items[j] = key`의 배열 쓰기 횟수다. 제자리 마지막 쓰기도 1회다. 지역 변수 key로 복사하는 일과 tag/key 멤버 수는 세지 않는다. 원소가 0·1개면 두 횟수 모두 0이다. 이는 이번 구현 과제의 계수 규약이지 모든 정렬의 공통 정의는 아니다.

## 5. 독자 정적 도식과 단계별 추적
도식 stable-insertion-counts는 `2:20, 1:10, 2:21`을 추적한다. i=1: 2>1은 참 → 2:20 오른쪽 이동 → 1:10 삽입, 비교1·이동2. i=2: 2>2는 거짓 → 같은 자리에 2:21 기록, 비교1·이동1. 합계 비교2·이동3이다. 두 2의 태그 20→21 순서는 그대로다.

## 6. 함수 계약·빈 범위·실패 보존
`int stable_sort_counted(struct SortItem items[], size_t count, size_t *out_comparisons, size_t *out_moves)`를 작성한다. count는 0..8이다. count>0이면 호출자는 count개 이상의 살아 있는 쓰기 가능한 연속 원소를 제공한다. count=0이면 items=NULL도 허용하고 배열을 읽거나 쓰지 않는다. 두 출력은 모두 살아 있는 쓰기 가능한 서로 다른 size_t 객체이며 배열 객체 전체와 겹치지 않는 것이 호출자 전제다. NULL 출력·count>8·양수 count의 NULL 배열은 원소 접근 전 실패0, 유효한 출력과 배열을 보존한다. 성공1이면 [0,count)만 정렬하고 이번 호출의 횟수를 출력한다. 길이가 작은 양수라도 NULL 출력은 실패다. 임의 포인터 유효성은 검출할 수 없다.

## 7. 단계별 예제: 완성 프로그램
관찰용 전체 프로그램이다. 제출창에는 stddef.h·구조체·stable_sort_counted만 넣고 main·printf는 넣지 않는다.
```c
#include <stddef.h>
#include <stdio.h>

struct SortItem { int key; int tag; };
int stable_sort_counted(struct SortItem items[], size_t count,
                        size_t *out_comparisons, size_t *out_moves) {
    if (out_comparisons == NULL || out_moves == NULL || count > 8
        || (count > 0 && items == NULL)) return 0;
    size_t comparisons = 0;
    size_t moves = 0;
    for (size_t i = 1; i < count; ++i) {
        struct SortItem key = items[i];
        size_t j = i;
        while (j > 0) {
            ++comparisons;
            if (!(items[j - 1].key > key.key)) break;
            items[j] = items[j - 1];
            ++moves;
            --j;
        }
        items[j] = key;
        ++moves;
    }
    *out_comparisons = comparisons;
    *out_moves = moves;
    return 1;
}

int main(void) {
    struct SortItem items[] = {{2,20}, {1,10}, {2,21}};
    size_t comparisons = 777;
    size_t moves = 888;
    if (!stable_sort_counted(items, 3, &comparisons, &moves)) return 1;
    printf("%d:%d %d:%d %d:%d\n", items[0].key, items[0].tag,
           items[1].key, items[1].tag, items[2].key, items[2].tag);
    printf("%zu %zu\n", comparisons, moves);
    return 0;
}
```
컴파일: `gcc -std=c11 -Wall -Wextra -Wpedantic -Werror example.c -o example`.

## 8. 실제 출력과 이유
첫 줄 `1:10 2:20 2:21`, 둘째 줄 `2 3`이며 각 줄 끝에 줄바꿈이 있다. 비교2·이동3의 근거는 5절의 두 반복이다. 채점 공개 예시 `1 2 3 1:10 2:20 2:21`은 별도 하네스가 성공 여부·횟수·결과 레코드를 한 줄로 출력한 것이다. 제출 함수의 표준 출력은 없어야 한다.

## 9. 흔한 오류와 심화
`>=`로 같은 키까지 밀면 불안정하다. 거짓 비교를 빼거나 마지막 제자리 쓰기를 빼면 정렬 배열은 맞아도 계수 계약을 어긴다. 이전 호출 횟수를 더하지 말고 매번 0부터 센다. NULL/길이 검증 전에 출력777·888을0으로 바꾸지 않는다.
<details><summary>심화: 연산 수와 실제 실행 시간은 다르다</summary>
일반 n개에서 이 삽입 정렬은 이미 정렬된 입력의 키 비교와 배열 쓰기가 각각 n-1회이고, 역순의 키 비교는 n(n-1)/2회·배열 쓰기는 그 값+n-1회다(n≥1). 따라서 이 비용 모델에서 최선 시간 O(n), 최악 O(n²), 추가 공간 O(1)이다. 실제 초 단위 시간·컴파일러 최적화 결과를 보장하지 않는다. 최대8의 과제는 계수 연습용이다. 키를 빼서 비교하면 정수 넘침 위험이 있으므로 관계 연산으로 비교한다. 구조체는 멤버별로 검사하고 패딩 바이트를 비교하지 않는다.
</details>

## 10. 중간 점검·핵심 요약·퀴즈
이미 정렬된 두 레코드를 처리할 때는? ①비교0·이동0 ②비교1·이동0 ③비교1·이동1 ④태그순 재정렬. 정답③. 거짓 키 비교와 마지막 제자리 배열 쓰기를 모두 포함한다. 안정성은 같은 키의 원래 순서, 정렬은 키의 순서, 연산 수는 명시한 계수 규약이다. 셋을 따로 확인한다.

## 11. 직접 풀기·기초·응용·도전·Mini Project
기초: 두 원소 역순을 손으로 추적한다. 응용: 키가 모두 같은 네 레코드의 태그 순서를 확인한다. 도전: 8개 역순에서 비교28·이동35, 접두부3개만 정렬할 때 뒤 원소 보존을 확인한다. Mini Project: 같은 4개 레코드의 정렬·역순·중복 입력을 표로 만들고 예상/실제 비교·이동을 따로 적는다. 동일 키의 태그를 일부러 숫자 역순으로 두어 안정성을 점검한다.
