# CodeWeave 지속 개발 운영 규칙

2026-10-14 사용자의 새 운영 규칙이다. 일회성 작업이 아니라 모든 예약 실행에 적용한다. 이 파일이 이전 대화·예약의 개발 지시·과거 로드맵과 충돌하면 이 파일을 우선한다. 실제 GitHub/CI 결과 없이 완료 상태를 추정하지 않는다.

저장소: https://github.com/cys123431-ship-it/CodeWeave (`main`). 목표는 교과서형 이론과 직접 풀고 재제출하는 실습의 결합이다. 0→1→2단계 순서로 진행하며 1·2단계가 끝나기 전 새 단원·문제를 추가하지 않는다.

## 실행 시작

1. 이 파일을 먼저 읽고 맨 위의 현재 단계를 확인한다. 인수인계 문서는 이 파일과 `docs/DEVELOPMENT_LOG.md`의 최근 2건만 읽는다. 선택한 항목의 관련 소스·검사는 필요한 만큼 읽는다.
2. 실행 첫 기록의 첫 줄을 반드시 `AUTONOMOUS_DEVELOPMENT.md 현재 단계: ○○ 확인함`으로 남긴다. ○○에는 실제 현재 단계를 넣는다. 이 기록이 없으면 새 규칙의 적용 증거가 없는 것으로 본다.
3. 최신 GitHub main HEAD/트리/CI/관련 PR과 로컬 미커밋 작업을 실제 조회한다. 과거 HEAD나 scratch/대화 기억을 최신이라고 가정하지 않고 기존 미완료 변경을 보존한다.
4. 결과 SHA의 CI가 실패했다면 그 실패 수정이 다음 실행의 첫 작업이다. 그렇지 않으면 현재 단계의 가장 앞선 미완료 항목 하나를 선택한다.
5. 분석·계획만 보고하지 말고 안전하게 승인된 코드·검사·문서를 실제 수정·실행 검증·재검토해 항목별 작은 커밋 또는 PR로 반영한다.

## 0단계 — 예약 작업에 규칙 반영

### 0-1. 지침 파일 저장
- 이 문서에 1·2단계, 상시 규칙과 보고 형식을 보존한다. 충돌하는 기존 규칙을 대체하고 삭제/대체 목록을 보고한다.
- 맨 위의 현재 단계는 단계가 끝날 때마다 갱신한다. 현재 단계 전환과 완료 기록은 실제 검증 근거로만 한다.

### 0-2. 예약 지시문 갱신
- 기존 CodeWeave 예약의 지시문을 다음으로 교체한다. 새 예약을 만들거나 다른 예약을 변경하지 않는다.
- “CodeWeave 저장소의 docs/AUTONOMOUS_DEVELOPMENT.md를 먼저 읽고, 그 파일의 '현재 단계'와 규칙에 따라 작업하라. 이 파일의 규칙이 다른 모든 이전 지시보다 우선한다.”
- 수정 도구가 없거나 거부되면 수정 불가를 정확히 보고한다. 성공 후 재조회하여 실제 저장된 지시문과 기존 일정/활성 상태를 대조한다.

### 0-3. 반영 확인
- 다음 실행은 이 파일을 먼저 읽고 실행 시작의 확인 문장을 일지 첫 줄에 기록한다. 기록 부재는 규칙 미적용으로 간주한다.
- 원격 파일·현재 단계·일지 표식을 실제 읽고 확인한다. 지침 저장과 실제 다음 예약 실행의 적용 확인을 혼동하지 않는다.

## 1단계 — dev-server.mjs 보안·정확성 수정

### 1-1. 로컬 CSRF / DNS rebinding 차단
- loopback 바인딩만으로 안전하다는 전제를 금지한다. POST /api/grade에 아래 네 조건을 모두 요구한다.
- Content-Type은 정확히 `application/json`, 그 밖에는 415.
- Host는 `127.0.0.1:PORT` 또는 `localhost:PORT`, 그 밖에는 403. PORT는 실제 서버 포트다.
- Origin이 있으면 `http://127.0.0.1:PORT` 또는 `http://localhost:PORT`, 그 밖에는 403.
- 서버 시작 시 무작위 토큰을 생성해 페이지에 주입하고 `X-CodeWeave-Token`과 일치할 때만 채점한다.
- text/plain·외부 Origin·위조 Host·토큰 누락 각각이 GCC 실행과 임시 디렉터리 생성 전에 거부되는지 검사한다.

### 1-2. 실행 자원 제한
- Linux/macOS 제출 실행은 detached 별도 프로세스 그룹으로 하고 시간 초과 시 그룹 전체를 종료한다.
- ulimit 또는 prlimit으로 CPU 시간·가상 메모리·파일 크기·프로세스 수를 제한한다.
- Windows에 적용되지 않는 제한을 README 제한 섹션에 한 줄로 명시한다.
- fork 후 sleep하는 자식이 채점 후 남지 않음, 큰 malloc 루프가 제한에 걸림을 검사한다.

### 1-3. 결과 개수 표시
- 치명적 오류로 중단한 뒤의 남은 모든 사례를 “미실행”으로 tests에 포함한다.
- 결과 메시지는 통과 수/전체 사례 수다.

### 1-4. 크기 제한 일관화
- 본문 바이트 제한은 코드 최대 길이 × 4 + 여유분으로 맞춘다.
- 한글 25,000자 코드가 허용되는지 실제 요청 검사한다.

### 1-5. 컴파일 옵션 일치
- 채점기 -Wall/-Wextra와 본문의 -Wpedantic/-Werror 정책 중 하나로 통일한다.
- 경고를 실패로 처리하는지 결정하고 ARCHITECTURE.md에 한 줄 기록한다.

### 1-6. 가독성 리팩터링
- 동작 변경 없이 grade()를 parseRequest, writeSources, compile, runCases, buildResult로 분리한다.
- 한 줄에 문장 하나, 정상 들여쓰기. 전후 npm test 결과가 같아야 한다.

## 2단계 — 개발 프로세스 정리

### 2-1. 개발 일지 축소
- 기존 DEVELOPMENT_LOG 기록을 docs/log/2026-10.md에 보존·이동하고 본 파일은 최근 5건만 남긴다.
- 2026-10 원본은 `docs/log/2026-10.manifest.json`의 시작 SHA·blob·바이트·SHA256으로 검증하는 불변 접두부다. 과거 원문은 재작성하지 않으며 반복 제약은 활성 일지에서만 빼고 상시 제약을 참조한다.
- 앞으로 새 기록을 맨 앞에 추가하고 6번째부터의 원문은 해당 월 보관 파일 뒤에 덧붙인 뒤 활성 파일에서 뺀다. manifest의 원본 접두부는 교체하지 않는다. 최근5건은 고정 필드로 유지하고 상세 증거는 보관 문서로 연결한다.
- 앞으로 1건은 확인 문장을 포함해 15줄 이내. 필드: 시작/결과 SHA, 목표, 변경 파일 수, 테스트 결과(숫자), CI URL/결과, 발견한 문제, 단계별 완료율, 다음 작업.
- 반복 면책은 아래 상시 제약에만 두고 일지에서는 뺀다. 시작 시 이 지침과 최근 일지 2건만 읽는다.
- 커밋은 자기 SHA를 미리 알 수 없으므로 결과 SHA를 만들어 넣지 않는다. 실제 확인한 결과 커밋/CI는 후속 기록·보고에 남기고 현재 커밋 제목으로 연결한다.

### 2-2. README 정리
- 150줄 이하: 소개, 빠른 시작, 기능 요약(단원·문제 수), 꼭 확인할 제한, 문서 링크.
- 문제별 사례 수·경계값 등 상세는 C_EXERCISE_AUDIT.md로 이동한다.

### 2-3. 반복되는 의례적 점검 중단
- 로컬 Playwright Chromium을 한 번 설치해 해결한다. 불가능하면 상시 제약에 “로컬 UI는 CI에서만 검증”을 한 번 기록하고 반복 시도하지 않는다.
- PDF는 특정 절의 구성을 실제로 참고할 필요가 있을 때만 연다. 표지 렌더링·크기 확인을 매 실행 반복하지 않는다.

### 2-4. 테스트 품질 정리
- 절 개수·줄 수·특정 문장 표현을 강제하는 콘텐츠 검사 목록을 만들고, 그중 필수 헤딩 존재·예제 컴파일만 남겨 나머지를 삭제한다.
- 채점 결과·저장/백업 호환성·컴파일 가능성·보안 거부 같은 동작을 검증한다.
- 통과를 위해 기대값이나 본문 문장을 고치지 않는다. 정당한 수정이 꼭 필요하면 이유를 일지 한 줄로 기록한다.

### 2-5. 학습자 관점 점검
- c-hello/c-types/c-loops를 C 입문자 관점으로 다시 읽는다.
- 본문은 핵심 설명·예제·실습 중심, 표준 조항·구현 정의 등은 접을 수 있는 심화 블록으로 이동한다.
- 30분 초과 단원은 분할 방안을 제안한다.

### 2-6. 확정 로드맵과 트랙 균형
- ROADMAP의 “초안”을 없애고 A~I 각 단계에 제목 수준 단원 5~12개를 확정한다. 각 단원은 완료/진행 중/미착수로 표시한다.
- 문서 맨 위에 단계별 완료율 표를 두고 실행마다 실제 근거로 갱신한다. 확정 전 분모·검증 없이 완료율을 만들지 않는다.
- 1·2단계가 끝난 뒤 새 단원은 자료구조(D)→알고리즘(E)→Rust(F~G)→C(C단계 남은 부분) 순환이다. C를 연속 두 번 선택하지 않는다.
- 자료구조·알고리즘은 C로 구현하고 기존 GCC 함수형 채점을 재사용한다. 리스트·스택·큐부터 시작한다.
- Rust 첫 작업은 cargo test 기반 채점기 설계이며 기존 c-function과 같은 구조로 설계한다. 채점기 구현 전 단원은 이론·퀴즈만 제공하고 실제 실습 채점/숙달 완료를 주장하지 않는다.
- 새 단원은 화면 10~15절, 원고 150줄 이내, 채점 사례 8~12개다. 기존 C 25~29절/250~400줄은 새 기준이 아니다.
- 단원 1개는 1회, 최대 2회 실행 안에 끝낸다. 미완료 시 검증 가능한 범위를 줄이고 나머지는 다음 단원으로 넘긴다. 기존 승인 계약을 몰래 축소하거나 필수 검사를 제거하지 않는다.
- 깊은 표준 해설보다 핵심 개념·예제·실습을 우선한다.

## 상시 규칙

- 모든 수정은 먼저 실패하는 검사를 작성한 뒤 수행하며 항목 단위로 커밋을 나눈다. 문서 지침은 필수 구조/상태/인수인계 계약을 검사하고 교육 문장 표현을 테스트에 맞추지 않는다.
- 1회 기능 1개, 변경 파일 10개 이하. 작업 중 사용자 수정 지시가 오면 가장 최신 지시를 먼저 반영한다.
- 결과 SHA의 CI 성공 URL을 확인한 뒤에만 “완료”로 기록한다. CI 실패는 다음 실행 최우선이다.
- 기능 추가마다 외부 입력·코드 실행·파일 접근의 보안 영향을 한 줄로 일지에 기록한다.
- npm test, 변경 JS/MJS node --check, git diff --check, GCC/API와 필요한 화면 검사 실행. 실패를 수정하고 재검사하되 불필요한 반복은 하지 않는다.
- 원격 최신 HEAD 확인·expected SHA·기존 base tree 보존·비강제 갱신을 사용한다. 원격 변경/충돌은 읽고 합친 뒤 다시 검사한다.
- 원격 HEAD/변경 파일/CI를 실제 재조회하고 결과 SHA/URL/브랜치를 보고한다. skip·미실행·CI 대기를 성공으로 포장하지 않는다.

## 상시 제약

- CodeStep 변경/혼합, 이유 없는 전체 React 재작성/서비스 이전, AI 개인 멘토/챗봇/튜터, 복잡한 런타임 애니메이션 금지. 독자 정적 SVG·표·그림은 허용한다.
- 기존 정상 코드와 진도/초안/제출 키·백업 v1을 보존한다. 이론·퀴즈·실습·복습·전체 숙달은 구분하고 채점 없는 트랙의 숙달을 완료로 표시하지 않는다.
- dev-server는 신뢰하는 개인 C만 실행하는 로컬 개발 도구다. loopback·CSRF 방어·시간/자원 제한은 프로세스/파일/네트워크 격리나 샌드박스가 아니다.
- 임의 C/Rust 호스트 실행 API를 인터넷에 배포하지 않는다. 공개 실행은 비루트·CPU/메모리/시간/프로세스·파일/네트워크·위변조·악성 제출 대응을 별도로 검증해야 한다.
- GitHub 저장은 웹 호스팅/배포가 아니다. 실제 Windows/Android/태블릿/PWA 설치는 CI Chromium 화면·390px·오프라인 검사와 구분한다.
- PDF 원본·본문 대량·캡처·상용 문제를 복제하지 않는다. 참고가 필요할 때 해당 절만 실제 읽고 범위를 기록한다. Express 개정4판/K&R 2판은 개인 참고용이다. 외부 교육 구조 참고시 원문/라이선스를 확인한다.
- 코드는 독립 작성하고 조각/완성 프로그램을 구분해 실제 컴파일한다. 정의되지 않은/구현 의존 동작을 C 언어 보장으로 설명하지 않는다.
- 저장소 삭제·대규모 덮어쓰기·main force push·사용자 데이터 삭제·기밀 공개·보호/인증 해제·유료 API/서비스·저장소 이전·미검증 공개 실행은 승인 없이 금지.
- 새 예약 생성이나 일시 실패에 임의 예약 취소를 하지 않는다. 정확한 오류·읽기/쓰기·검사 범위를 기록하고 반영 불가한 패치/검사를 보존한다.
