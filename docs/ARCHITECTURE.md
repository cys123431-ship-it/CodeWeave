# CodeWeave 아키텍처 (2026-10 초기 제안)

## 목적

개인용 PWA에서 C·Rust·자료구조·알고리즘을 **교과서 수준으로 학습하고 Exercism처럼 직접 풀고 실제 테스트로 검증**한다. AI 개인 멘토링 및 런타임 메모리 애니메이션은 제외한다. 필요할 때 정적인 교육 그림과 표를 사용한다.

## v0.1 범위

- 의존성 없는 브라우저 UI: `index.html` + `styles.css` + ES modules
- 로컬 진도·풀이 코드 저장, 백업·복원, 네 트랙과 20개 시범 단원
- 자동 채점: 브라우저 개념 퀴즈 20개 + **개인 PC용 C 컴파일/테스트 API 17개**
- PWA: service worker가 정적 자산을 저장하고 네트워크가 없어도 이론/퀴즈/임시 코드를 제공
- 모바일 브라우저: 반응형 콘텐츠/읽기/퀴즈/임시 코드 작성. 모바일 단독 로컬 컴파일 불가

## 중요한 보안 경계

`dev-server.mjs`는 제출된 임의 C 코드를 운영체제에서 직접 실행한다. **컨테이너 샌드박스가 아니다.** 오직 신뢰할 수 있는 본인의 코드만 입력하는 개발 환경에서 사용해야 한다. 서버는 `127.0.0.1`로만 바인딩한다. 공용 인터넷/캠퍼스 네트워크에 노출하지 않는다. 시간 초과와 출력 크기 제한은 보조 조치일 뿐 파일 접근이나 네트워크 통신을 막지 않는다.

인터넷에서 모든 사용자가 C/Rust 코드를 자동 채점하도록 하려면 별도의 격리된 제출 워커/큐/저장소를 구축한다. 예시: 컨테이너 기반 실행 (비루트, seccomp, 네트워크 비활성, CPU/메모리/시간 제한, 읽기 전용 파일시스템, 프로세스 수 제한, 실행 결과 검증). 사전 검증 완료까지 외부 코드 실행 API는 공개하지 않는다.

### 로컬 정적 파일 접근 정책

`server/static-files.mjs`는 현재 브라우저가 사용하는 20개 파일을 정확한 경로로 허용한다. `/`는 `index.html`로 연결하고 정상 query와 GET/HEAD를 지원한다. 디렉터리 전체를 공개하지 않으므로 `.git`, `.env`, 서버/테스트/문서/원고와 미등록 `src`·`assets` 파일은 404다. 새로운 학습 자산은 허용 목록과 정적 서버 회귀 검사에 함께 등록해야 한다.

원래 요청 경로를 URL 정규화 전에 검사하여 점 경로, 중복 구분자, 역슬래시, 인코딩된 구분자/중복 인코딩, 잘못된 UTF-8/퍼센트 인코딩과 제어 문자를 400으로 거부한다. 허용된 파일도 부모 디렉터리와 파일의 심볼릭 링크를 거부하고 실제 경로를 확인한다. 지원되는 OS에서는 최종 파일을 `O_NOFOLLOW`로 열며 열린 파일의 메타데이터와 스트림을 사용한다. HEAD와 연결 종료 시 파일을 닫고 읽기 오류는 응답 연결을 종료한다.

이 정책은 신뢰하는 로컬 체크아웃의 HTTP 파일 제공 범위를 좁히는 조치다. 악의적인 프로세스가 파일시스템을 동시에 교체하는 환경이나 제출된 C 프로그램의 파일·네트워크 접근을 격리하는 경계가 아니다. `tests/static-server.test.mjs`는 실제 비밀 대신 임시 프로젝트의 합성 파일로 차단을 재현하고 모든 PWA shell 자산과 기존 API 경로를 검사한다. 브라우저 동작은 별도 Chromium CI로 확인한다.

## 향후 권장 구조

```text
apps/web        → React + TypeScript PWA (UX 안정화 후 전환 가능)
apps/api        → 제출 수집·인증·점수 판정 API
workers/runner  → C/Rust 컨테이너 기반 격리 컴파일·실행
packages/content → 구조화된 MDX, 코드 예제, 그림, 체크 문제
packages/tests   → 언어별 공개/비공개 테스트 정의
supabase         → 계정·진도·풀이 동기화 (선택)
```

현 프로토타입은 모든 학습 경로·점수·코드가 브라우저에만 있으므로 **로그인, 모바일과 PC 동기화, 중앙 저장, 채점 기록 검증** 등은 미구현 상태다.

## Exercism에서 차용할 교육 설계

- Track 별 강의·연습문제
- Concept / Practice Exercise 구분
- Starter code → 자체 작성 → 테스트 실행 → 실패를 수정하여 재제출
- 같은 문제의 반복 제출(iterations) 및 테스트 주도 학습(TDD)
- Learning Mode / Practice Mode, 선수 개념과 복습 큐
- 오류를 정답 코드 제공이 아니라 피드백과 설명으로 연결

**참고할 학습 방식과 재사용 가능한 소스의 구분:** Exercism 트랙별 LICENSE, 콘텐츠 출처, 개별 코드를 사전 확인한다. 현재 저장소에는 타 프로젝트의 코드나 교재 원문을 복제하지 않는다.

## 통합 백업과 기존 형식 호환

`src/backup.js`는 `full-backup` v1 형식으로 퀴즈 진도, 모든 트랙의 코드 초안, 문제별 최근 제출 이력을 한 파일에 저장한다. 두 화면은 내보내기 직전에 localStorage의 최신 세 키를 다시 읽으므로 열려 있던 화면의 오래된 메모리 상태를 백업하지 않는다. 가져오기는 알려진 단원만 허용하고 코드·진단·테스트 수와 길이를 기존 제한으로 정규화한다. UI는 5MB보다 큰 파일을 JSON으로 읽기 전에 거부한다.

기존 `CodeWeave version:1` 진도 파일은 진도·초안만 교체하고 독립 제출 이력을 유지한다. 기존 `kind:attempt-history version:1` 파일은 C 연습 범위의 초안·제출만 교체하고 퀴즈 진도와 Rust 등 다른 트랙 데이터를 유지한다. 새 통합 형식은 세 범위를 모두 교체한다. 세 localStorage 키를 쓰는 도중 오류가 나면 이미 변경한 키를 이전 원문으로 되돌리며, 자동 복구까지 실패한 경우 이를 별도 오류로 알린다. localStorage 자체는 트랜잭션 데이터베이스가 아니므로 복원 전 파일 백업을 계속 권장한다.

PWA shell v21은 통합 백업·숙달 계산·문제 메타데이터·다중 파일 직렬화·컴파일 진단 분류 모듈, 여덟 함수 실습과 `fgets`·`strtol` 전체 프로그램 실습 카탈로그를 오프라인 자산에 포함한다. 실제 Chromium CI는 연습장에서 통합 파일을 내려받아 다시 복원하고, 다중 파일 세 소스와 제출 이력 및 기존 진도 v1도 복원하며, 이후 오프라인 재로딩까지 검사한다.

## 학습 상태와 숙달 판정

기존 `codeweave.progress.v1` 키를 유지하면서 `theoryRead`와 수동 `review` 단원 ID 배열을 추가한다. 필드가 없는 기존 기록은 빈 배열로 정규화하므로 퀴즈 통과만으로 이론 읽기나 숙달을 추정하지 않는다. 퀴즈 통과는 기존 `completed`, 실습 통과는 `codeweave.iterations.v1`의 성공 제출에서 각각 계산한다.

`src/mastery.js`는 저장 형식과 UI 사이의 순수 계산 경계다. 채점기가 등록된 단원은 이론·퀴즈·성공 제출을 모두 갖고 복습이 불필요할 때만 전체 숙달이다. 최신 퀴즈 결과나 최신 실습 제출이 실패했거나 수동 복습 표시가 있으면 과거 통과 이력을 지우지 않고 숙달만 보류한다. 채점기가 없는 Rust·자료구조·알고리즘 단원은 실습 통과와 전체 숙달을 주장하지 않는다. 통합 백업 v1은 새 배열을 선택 필드로 보존하며 두 기존 v1 파일은 빈 배열로 안전하게 이관한다.

## 문제 메타데이터와 채점 정의

`src/exercises.js`는 20개 시범 연습의 공개 메타데이터를 제공한다. 각 정의에는 고유 ID, Concept/Practice 유형, 언어, 선수 단원, 핵심 개념, 채점기 종류와 공개 예시가 있다. 다중 파일형은 필수 파일명 목록도 가진다. 모듈을 불러올 때 중복 ID, 지원하지 않는 열거값, 빈 개념, 자기 참조·알 수 없는 선수 단원, 잘못된 예시와 파일 계약을 거부한다.

`server/grading-exercises.mjs`는 브라우저에 제공하지 않는 실제 GCC 사례와 함수 테스트 하네스를 보관한다. `stdin-output`, `c-function`, `c-multi-file`로 선언한 문제는 사례가 반드시 있어야 하고, 함수형은 비어 있지 않은 하네스와 사례별 실행 인수도 필요하다. 채점 불가 문제·알 수 없는 ID에 사례를 붙이거나 함수형이 아닌 문제에 하네스를 붙이면 서버 시작 단계에서 실패한다. 공개 예시는 최소 한 개의 실제 사례와 일치하는지 자동 검사한다. 앱의 숙달 판정과 반복 제출 연습장도 트랙 이름이 아니라 이 메타데이터의 채점기 등록 여부를 사용한다.

`src/compiler-feedback.js`는 GCC/ld 실패 원문의 결정적인 패턴만 분류한다. 누락 헤더, 선언·정의 형식 충돌, 미정의 참조, 중복 정의와 일반 컴파일/링크 오류를 고정된 한국어 제목·점검 항목으로 반환하며, 컴파일러 실행 불가·시간 초과도 소스 오류와 구분한다. 서버는 원문 `compileOutput`을 그대로 유지한 채 `compilerFeedback`을 추가한다. 브라우저는 허용된 고정 값만 검증하여 결과와 제출 이력에 저장하므로 임의 서버 문자열을 신뢰하지 않는다. 선택 필드가 없는 기존 iteration/full-backup v1은 계속 읽고, 알 수 없는 피드백 값은 원문을 보존한 채 버린다.

함수 구현형 `c-function`은 제출 소스를 `submission.c`, 신뢰된 서버 하네스를 `harness.c`로 저장해 하나의 실행 파일로 링크한다. 하네스가 제공하는 `main`이 제출 함수를 여러 인수로 호출하므로 사용자가 `main`을 함께 제출하면 중복 정의로 컴파일·링크가 실패한다. 반환값은 하네스 출력과 사례별 예상값으로 비교하며, 제출 함수가 남긴 표준 출력도 결과에 섞여 부작용 실패로 드러난다.

두 번째 함수형 문제 `c-array-max-function`은 같은 채점 경로를 변경하지 않고 새 공개 계약·비공개 하네스만 등록한다. `const int[]`와 `size_t` 길이, `int *out_max`를 함께 사용하며 정상·모든 음수·중복·한 원소·표현 범위 끝값, `NULL` 배열·0 길이·`NULL` 출력 포인터를 검사한다. 실패 시 sentinel 출력값이 유지되는지도 비교하므로 반환값만 맞고 출력 객체를 먼저 덮어쓰는 구현을 구분한다. `INT_MAX` 자체를 고정된 32비트 숫자로 가정하지 않고 하네스 안에서 기호 상수와의 일치 여부를 검사한다.

세 번째 함수형 문제 `c-string-count-function`은 `const char *`의 첫 널 문자 전까지 특정 문자를 세어 `size_t *out_count`에 기록한다. 빈 문자열·반복·대소문자·대상 없음과 `target == '\0'`을 검사하고, `NULL` 문자열 실패에서는 sentinel 결과가 유지되어야 한다. 포인터만으로 실제 버퍼 경계를 확인할 수 없으므로 올바르게 널 종료된 읽기 가능한 문자열은 호출자 전제로 명시하며, 이 하네스는 메모리 오류 탐지기나 격리 경계가 아니다.

네 번째 함수형 문제 `c-bounded-string-length`는 `buffer`와 `capacity`를 함께 받아 `[0, capacity)` 안의 첫 널 문자 인덱스를 `size_t *out_length`에 기록한다. 마지막 허용 칸은 성공하지만 범위 바로 밖의 종료 문자는 읽지 않으며, 비종료 버퍼·용량 0·포인터 오류에서 실패하고 출력 sentinel을 보존한다. 호출자가 `capacity`개의 읽기 가능한 객체를 제공해야 한다는 전제는 여전히 필요하며, 경계 인수 자체가 임의 포인터를 검증하거나 샌드박스를 제공하지는 않는다.

다섯 번째 함수형 문제 `c-struct-student-score`는 `struct Student { int id; int score; }` 객체의 주소와 변화량을 받아 유효한 현재 점수와 요청 결과를 모두 0~100으로 제한한다. 11개 사례가 정상·0/100 경계·0 변화량·범위 밖 결과·잘못된 현재 상태·`NULL`·`INT_MIN`/`INT_MAX`를 검사한다. 구현은 signed 덧셈 전에 `delta < -score || delta > 100 - score`를 판정하고, 모든 검증 뒤 `score`만 바꿔 실패 시 객체 전체와 성공 시 `id`를 보존해야 한다. 이 하네스도 구조체 포인터가 실제 유효 객체를 가리키는지 일반적으로 증명하거나 실행을 격리하지 않는다.

여섯 번째 함수형 문제 `c-struct-array-search`는 `const struct Student students[]`와 별도 `count`를 받아 `id`가 같은 첫 원소의 인덱스를 출력 객체에 기록한다. 11개 사례가 첫·중간·마지막·단일 원소, 미발견, 중복의 첫 위치, `NULL` 배열·0 길이·`NULL` 출력, `INT_MIN` 학번을 구분한다. 성공하기 전에는 출력 객체를 쓰지 않고 `[0, count)`만 읽어야 한다. 포인터가 실제로 `count`개 객체를 가리키는지는 하네스가 일반적으로 증명할 수 없으며 로컬 실행 격리도 제공하지 않는다.

일곱 번째 함수형 문제 `c-struct-array-sort`는 수정 가능한 `struct Student students[]`를 `id` 오름차순으로 안정 정렬한다. 11개 사례가 이미 정렬·역순·단일·중복·모든 키 동일·`INT_MIN`/`INT_MAX`·음수와 양수·두 종류의 빈 범위·양수 길이의 `NULL`을 구분한다. 레코드 전체 이동, 동등 키 상대 순서와 `count == 0`이면 `NULL`도 성공한다는 계약을 검사한다. 비교 뺄셈 대신 관계 연산자를 사용해 signed overflow를 피하지만, 포인터가 실제로 `count`개 객체를 가리키는지는 일반적으로 증명하거나 격리하지 않는다.

여덟 번째 함수형 문제 `c-struct-array-binary-search`는 `id` 오름차순으로 정렬된 `const struct Student students[]`에서 목표 학번의 첫 위치를 찾는다. 12개 사례가 첫·중간·마지막·단일 원소, 중복의 첫 위치, 미발견, 두 종류의 빈 범위, 양수 길이의 `NULL`, `NULL` 출력 포인터와 정수 극값을 구분한다. `[left, right)`와 `left + (right - left) / 2`를 사용하고 일치해도 오른쪽 경계를 줄이는 lower-bound 구현을 요구하며, 실패 시 출력 sentinel을 보존한다. 정렬 여부와 실제 객체 범위는 호출자 전제이고, 유한한 기능 사례만으로 모든 입력에 대한 로그 복잡도를 증명하지는 않는다.

전체 프로그램형 `c-fgets-logical-line`은 `char chunk[8]`을 반복 사용해 첫 개행 전까지의 바이트 수를 누적한다. 짧은 줄, 빈 줄, 정확히 7바이트 뒤 개행, 8바이트와 여러 조각, 개행 없는 마지막 줄, 즉시 EOF, 두 번째 줄 무시를 9개 사례로 구분한다. 성공 조각의 널 종료와 입력 개행은 서로 다른 경계이며, `NULL` 반환 뒤 `ferror`를 먼저 검사한다. 현재 표준 입력 파이프 기반 하네스는 실제 읽기 오류를 결정적으로 주입하지 않으므로 그 분기까지 실행 검증했다고 주장하지 않는다.

후속 전체 프로그램형 `c-strtol-integer-input`은 `char line[64]`의 첫 줄을 10진수 `long` 하나로 검증한다. 정상 양수·0·음수, 앞뒤 공백, 숫자 없음, 부호만 있는 입력, 숫자 뒤 잔여 문자, 양·음 방향 `ERANGE`, 두 번째 줄 무시, 즉시 EOF, 정확히 63바이트와 64바이트 초과를 16개 사례로 구분한다. `endptr == line`, 초기화한 `errno`, `(unsigned char)`를 거친 `isspace`를 각각 검사하며, `long`의 고정 비트 폭을 가정하지 않는다. 표준 입력 읽기 오류 분기는 앞 문제와 마찬가지로 현재 파이프 사례로 실제 주입하지 않는다.

다중 파일형 `c-multi-file`은 브라우저에서 각 파일을 따로 편집하지만 `CODEWEAVE_MULTI_FILE_V1` 표식과 JSON payload를 합친 문자열 하나로 저장한다. 이 방식은 기존 draft/iteration/full-backup v1의 문자열 필드를 유지한다. `src/multi-file.js`는 파일명, 중복·누락·추가 파일, 파일 수, 개별 10,000자·전체 24,000자·직렬화 25,000자 한도를 양쪽에서 검증한다. 서버는 검증된 이름만 임시 디렉터리에 쓰고 `.c` 파일을 `-I` 헤더 경로와 함께 GCC에 전달한다. 헤더 누락과 정의 누락은 각각 컴파일·링크 진단으로 반환된다. 이 검증은 교육용 계약 검사이지 악성 코드 격리가 아니며 다른 C 채점기와 같은 로컬 전용 보안 경계를 갖는다. Rust 채점은 후속 유형이다.
